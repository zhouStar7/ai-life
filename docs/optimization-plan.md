# AI Life 项目优化方案

依据 AgentCompare 方案 D，基于 `main` 的 `c82b9c0`（1.0.1）制定。沿用本地优先和衣、食、住、行、支协同的方向，首版继续用现有 Web、Hono 和 SQLite。优化从日常记录能可靠保存开始，再降低录入成本，最后扩展到手机、外部助手和主动提醒。

## 一、当前基线与优先级

| 当前实现 | 对下一阶段的影响 |
| --- | --- |
| 前后端各有启动命令。后端首次建库会写入演示衣物、账单、行程和设备。 | P0 提供统一启动，正式数据从干净的库开始。旧库保留并提供迁移入口。[运行说明](../README.md#运行演示) · [初始化逻辑](../server/src/seed.ts) |
| 前端能读取本机接口的快照，也能从 IndexedDB 恢复上次成功读取的快照。部分写入失败后会转用内存数据，并沿用成功提示。 | P0 明确区分演示、本机已连接、离线缓存和写入失败。保存结果以服务端确认作为依据。[前端状态管理](../web/src/store.tsx#L239) · [快照缓存](../web/src/api/snapshot.ts) |
| 支出汇总固定筛选 `2026-09`，趋势混有演示值。饮食、衣橱、账单和差旅部分路径也仍用 `2026-09-22`，账单解析会把金额取整到元。 | P0 统一真实日期和报告周期，按分保存支出并兼容旧金额。缺失的账单日期交给用户确认。[支出汇总](../server/src/snapshot.ts#L30) · [饮食日期](../server/src/dietPlan.ts) · [账单解析](../server/src/adapters/bills.ts#L187) |

## 二、实施路线

### P0 · 第 1 周，从演示切到可长期使用的单机版

建议按下列顺序拆成三次可独立验收的改动。

| 顺序 | 交付范围 | 验收标准 |
| --- | --- | --- |
| 1. 统一启动与数据环境 | 根目录提供统一启动命令，复用前后端现有 npm 脚本。启动器检查端口和 API 就绪状态，退出时关闭两个子进程。演示库和个人库使用独立路径，个人库初始化只创建必要配置。同步调整当前会覆盖 `DATABASE_URL` 的 npm 脚本，确保初始化和运行指向同一个库。提供数据库备份、恢复及旧库迁移步骤。 | 干净检出安装依赖后，用一条命令打开前端并连上 API。个人库没有示例账单或行程，演示库可以独立体验。用旧库副本演练迁移和恢复，核对流水、衣物与行程数量。开发服务默认仅本机可达。 |
| 2. 修复日期、金额和保存反馈 | 前后端统一个人时区下的日期口径。餐食按日、支出按选定月份查询。明确手工记录的默认日期，导入时保留单据日期。将现有整数元按值迁为分，新增金额保留两位小数。真实模式写入失败时保留输入并显示重试入口。 | 覆盖月末跨月和本地午夜。上月流水留在上月，近六个月趋势来自实际入账数据。金额 `12.34` 导入后按 `12.34` 汇总，旧记录 `12` 仍显示 `12.00`。模拟接口中断后，页面标记缓存状态，保存失败有明确提示，恢复连接后重试并刷新仍能读回记录。 |
| 3. 配置诊断与跨模块试用 | 设置页增加 Ollama 手动探测与模型选择，分别验证文本和图片能力。天气首版由用户选城市，显示来源和更新时间。Home Assistant 先同步设备，再由用户选测试设备或绑定场景。差旅联动拆成预览和确认，家居动作独立确认，逐步展示执行结果。 | 无模型时仍能手工记餐、导入 CSV 和使用行程规则解析。天气请求失败时显示上次更新时间或天气未知。导入脱敏行程后可预览穿搭、打包、离家和预算，预览阶段无写入。重复确认只采纳一次，家居离线或部分执行失败时界面能指出失败项。 |

P0 通过后，先用七天验证三条路径。每天看一次今日概览，记录一次餐食或采用常用食谱。周末用一小批脱敏账单核对金额、日期和分类。下次出行时粘贴一条脱敏车票短信，检查时间线、打包清单和预算。真实 Home Assistant 连接在测试灯或专用场景上验收。

### P1 · 第 2–3 周，减少重复录入

| 场景 | 改动 | 验收标准 |
| --- | --- | --- |
| 周末对账 | 优先覆盖微信和支付宝常用 CSV 模板。保留平台流水号或来源标识，预览区分新增、重复和需要补全的行，导入结果列出各类数量。没有稳定流水号时把疑似重复交给用户确认。账单截图复用同一预览流程。 | 同一文件导入两次，第二次新增为零。两笔金额、商户相同但流水号不同的交易均保留。抽样核对分、分类、日期和合计。 |
| 随手记餐 | 复用规则估算、可编辑草稿和食谱一键复用，加上常用条目与份量调整。对未知份量明确标记估算。 | 常用餐食从打开入口到确认入账的中位耗时目标为 5 秒，按 10 次真实操作记录。陌生菜品可调整份量和营养估算，也可直接手工录入。 |
| 衣橱建档 | 先验证订单文本和照片草稿的批量编辑、保存，再用试用样本决定是否支持单张订单截图识别多件。相似衣物提示基于已有分类、颜色和名称，用户可继续保存。 | 用 10 件常穿衣物完成首批建档。至少用一张订单截图验证候选确认流程，逐件可修改或删除草稿。 |
| 行程准备 | 补齐常见铁路短信和航班邮件样本，改善解析预览与打包模板复用。预算分别显示本趟金额和所选月的出行金额。 | 一条铁路短信和一条航班邮件能走完解析、人工修正和保存。重复导入可辨认已有行程，打包模板复用后可以继续编辑。 |

### P2 · 第 4–6 周，把高频入口带到手机和外部助手

- **手机优先做查看和快速记录。** 先适配小屏上的今日概览、记餐和打包清单，再用 PWA 支持添加至主屏幕。受信 HTTPS 和访问控制就绪后，在一台实机完成安装和写入。离线首版提供最小范围的只读缓存，标明时间并支持清除。可验证手机断网时能查看缓存清单，联网后新增记录可在电脑端读到。
- **只选一条随手记通道试用。** 优先验证 iOS 快捷指令或 Android 等效入口，取决于试用设备。受限凭据只允许创建草稿，数据仍经现有服务校验。用正常提交、重复提交和撤销凭据逐项验收。聊天 Bot、短信和电子发票解析进入后续待办，依据真实记录频率和接入成本排序。
- **MCP 从只读工具起步。** 新建独立 MCP 服务入口，复用现有领域逻辑。首批提供穿搭建议、打包清单和预算摘要三个工具，用一个外部宿主验证发现、调用和权限。新增写入工具走应用内确认，限制可用动作并记录结果。

### P3 · 第 7 周起，按试用结果扩展

- **偏好和主动提醒。** 先采集可查看、修改和删除的显式偏好，例如怕冷程度、饮食禁忌和预算阈值。优先验证天气穿搭晨报和每周预算复盘，按本地时区去重并可关闭。离家巡检在用户授权后先发检查结果，待设备白名单、确认和失败处理验证通过，再评估自动执行。
- **本地备份和多端同步。** 单机恢复演练通过后，评估加密快照配合 WebDAV 或 NAS。先验证密钥恢复、版本回滚和旧数据兼容，再决定是否实现可并发编辑的多端同步。
- **共享类型和视觉主题。** 等前后端数据口径收敛后，提取共享接口类型并评估 npm workspaces。先从现有原型提取颜色、字体和间距变量，优先保证当前主题的手机可读性和键盘操作，再按使用反馈增加主题。[交互原型](../ai-life-designs/README.md) · [设计规范](design-system.md)

## 三、持续验证与发布

每周记录使用次数、查找或录入耗时、失败后是否需要重复输入，以及账单抽查差异。第一周记录基线，P0 验收要求新产生的真实记录在重新打开后可核对。P1 的周期导入验收要求重复导入无重复流水，抽样账单与应用汇总金额一致。每周优先修复影响数据可信度和阻断高频操作的问题，再用相同样本复测。

| 验证范围 | 做法 |
| --- | --- |
| 现有回归 | 安装依赖后运行 `npm --prefix server test`、`npm --prefix web run lint` 和 `npm --prefix web run build`。后端已有临时 SQLite 和阶段测试，可沿用来覆盖旧库及跨月数据。[后端脚本](../server/package.json) · [前端脚本](../web/package.json) · [后端测试](../server/src/phase1.test.ts) |
| 新增的关键回归 | 优先覆盖跨月与时区、金额转换、重复导入、保存失败和真实家居动作确认。首阶段完成后，将三条真实使用路径做成浏览器端到端回归。模型与 Home Assistant 的超时、无效返回和部分失败用替身验证。 |
| 发布与恢复 | 升级前保留一致的 SQLite 备份，在副本上验证迁移结果和回滚。账单、行程或照片送模型前，界面显示处理位置。本机模型作为默认选项，外部模型由用户显式选择。测试样本脱敏，日志和普通导出省略凭据。 |

## 四、现在如何试用

用 Node.js 24 从仓库根目录安装依赖，再启动个人模式。浏览器打开 `http://127.0.0.1:1117`。体验示例数据时运行 `npm run dev:demo`，打开 `http://127.0.0.1:1118`。升级前按运行说明备份个人库。[运行与恢复](../README.md#运行演示)

```sh
npm run setup
npm run dev
```

使用临时库和脱敏样本的本机回归已覆盖启动、迁移和恢复、跨月金额、断线保存、重导账单、餐食草稿及行程确认。模型、天气与家居异常使用替身验证。MCP 已通过外部 SDK 宿主发现并调用三个只读工具。[日常操作回归](../web/e2e/daily-use.test.mjs) · [MCP 宿主回归](../server/mcp/host.test.ts)

### 实际试用记录

- 连续七天查看今日概览并记录餐食。对常用餐食计时十次，从打开入口到确认入账，记录中位数、失败次数和是否需要重新输入。
- 用一批脱敏账单抽查日期、分类、精确到分的金额及第二次导入的回执。用十件常穿衣物和一张脱敏订单截图记录候选识别与修正次数。
- 用个人配置验证选定城市的天气以及模型的文字、图片能力。家居仅选试用灯或专用场景，记录实际动作和失败结果。
- 在一台手机上安装 PWA，断网查看打包清单并核对缓存时间，联网后记一餐并在电脑上读回。使用一条手机快捷入口测试提交、重试与令牌撤销。[手机安装](mobile-pwa.md) · [iOS 快捷指令](ios-meal-shortcut.md)

每次记录日期、设备、使用场景、耗时、结果及需要修正的地方。使用记录为 P3 的提醒频率、偏好字段、多端备份方式和主题取舍提供依据。
